# Recuperación léxica BM25 — CP-02

## Alcance y dependencia

`aether_lexical` implementa tokenización, índice invertido, estadísticas documentales,
puntuación BM25 y Top-K en C++20. Solo enlaza `aether_core` y la biblioteca estándar.
No depende de HNSW, distancias, VectorStore, CLI, RRF ni un modelo de embeddings.

Headers públicos en `include/aether/lexical/`; implementaciones en `src/lexical/`.
El namespace es **`aetherindex::lexical`**, respetando el namespace del repositorio.
`DocumentId` y `RankedResult` pertenecen a `aetherindex`, en core.

CP-02 no incorpora comandos de búsqueda textual a la CLI ni modifica QueryEngine.
RRF está disponible en [CP-03](rrf.md), la composición híbrida corresponde a CP-04
y la evaluación oficial Hit Rate@10 a CP-05. Tampoco introduce DocumentStore, generación de embeddings,
persistencia, actualizaciones/borrados, concurrencia ni técnicas WAND/pruning.

## Uso del componente

```cpp
#include "aether/lexical/bm25.hpp"

int main() {
    aetherindex::lexical::Bm25Index index({.k1 = 1.2, .b = 0.75});
    index.add_document(101, "motor motor e47");
    index.add_document(102, "motor temperatura");
    index.add_document(103, "bomba");
    index.build();

    const auto results = index.search("e47", 10);
    // Un resultado: document_id=101, score≈0.8142733421.
    return results.size() == 1 && results.front().document_id == 101 ? 0 : 1;
}
```

Desde un target CMake del proyecto:

```cmake
target_link_libraries(mi_consumidor PRIVATE aether_lexical)
```

El componente no imprime, no abre archivos ni finaliza el proceso.

## Identidad y contrato público

```cpp
// include/aether/core/types.hpp
using DocumentId = std::uint32_t;

// include/aether/core/search_result.hpp
struct RankedResult {
    DocumentId document_id;
    double score;
};
```

Se admite todo el rango de DocumentId, incluido cero. Son IDs externos estables;
no se sustituyen por posiciones de arrays. Aunque DocumentId y VectorId tienen
la misma representación uint32 en CP-02, su significado es independiente. La
futura aplicación resolverá explícitamente esa asociación.

| Método de `Bm25Index` | Contrato |
|---|---|
| Constructor con `Bm25Config` | `k1` finito y >0; `b` finito en [0,1]. Defaults 1.2 y 0.75. |
| `add_document(id,text)` | Solo durante construcción; duplica las frecuencias necesarias, no conserva referencias al texto original. |
| `build()` | Finaliza una sola vez y publica postings inmutables. |
| `search(query,k) const` | Solo después de build; K>0; devuelve hasta K candidatos. |
| `document_count()` | Cuenta documentos registrados, incluidos vacíos; accesible también durante construcción. |
| `average_document_length()` | Media de longitudes registradas, cero si no hay documentos. Se finaliza de nuevo al publicar build. |
| `is_built()` | Indica si terminó una construcción válida. |
| `inverted_index() const` | Acceso exclusivamente de lectura a postings y estadísticas. |
| `config()` | Copia de la configuración fija de la instancia. |

El resultado está ordenado por **score descendente** y, en igualdad exacta,
DocumentId ascendente. No hay IDs repetidos ni documentos sin coincidencias
añadidos para completar K. K mayor que el corpus es válido y no causa una
reserva de memoria proporcional a ese K.

La posición del resultado en el vector, más uno, define su rango para un futuro
consumidor RRF. Los scores BM25 se conservan para diagnóstico; no se suman con
distancias vectoriales. La prueba de contrato extrae esos rangos sin implementar
RRF ni ejecutar una búsqueda híbrida.

## Ciclo de vida, errores y fallos

```text
COLLECTING --add_document()--> COLLECTING --build()--> READY --search()--> READY
```

| Situación | Resultado |
|---|---|
| ID duplicado | `std::invalid_argument`; documento original y estadísticas intactos. |
| UTF-8 inválido en documento/consulta | `std::invalid_argument`. |
| Configuración inválida o K=0 | `std::invalid_argument`. |
| Buscar antes de build | `std::logic_error`, incluso con consulta vacía. |
| Insertar después de build o repetir build | `std::logic_error`. |
| Documento vacío o solo separadores | Se registra con longitud cero y participa en N y avgdl. |
| Consulta vacía, solo separadores o términos desconocidos | Ranking vacío después de validar estado y K. |
| Corpus sin documentos, o todos vacíos | Construcción válida; búsquedas válidas devuelven vacío sin dividir por avgdl=0. |
| Longitud documental >uint32 o total de tokens >uint64 | `std::length_error`. |
| Asignación fallida | Se propaga `std::bad_alloc`; inserción/build conservan su contenido lógico previo. |
| Score o normalización numérica no representable | `std::overflow_error`. |

La inserción prepara tokens y frecuencias localmente antes de incorporarlos al
mapa. Build prepara postings y longitudes en estructuras temporales; publica
READY únicamente después de completar todas las asignaciones y el ordenamiento.
Si falla build, el índice sigue COLLECTING, conserva las frecuencias y permite
agregar documentos o reintentar. Una búsqueda fallida no modifica el índice.

El índice es no copiable/no movible, como VectorStore, para mantener explícita
la propiedad y el lifetime de las vistas. Los spans de postings son de solo
lectura y permanecen válidos hasta destruir al propietario, porque solo se
obtienen en READY. No se establece un contrato de acceso concurrente en CP-02.

## Tokenización `ascii-tech-v1`

La política es única para documentos y consultas y no depende del locale:

- Convierte únicamente `A`–`Z` ASCII a minúsculas; conserva números y repeticiones.
- Conserva `-` y `_` dentro de identificadores; en los bordes o duplicados
  actúan como separadores: `HTTP_404`, `RTX-5090`, pero `foo--bar` son dos tokens.
- Conserva la forma `C++`, también seguida de dígitos como `C++17`.
  No conserva cualquier expresión con más: `x+y` produce `x`, `y`.
- Puntuación y controles ASCII separan. También se reconocen U+0085, U+00A0,
  U+1680, U+FEFF, U+2000–206F, U+3000–303F y los intervalos de puntuación
  U+FF01–FF0F, U+FF1A–FF20, U+FF3B–FF40, U+FF5B–FF65.
- Valida secuencias completas de UTF-8 según [RFC 3629](https://www.rfc-editor.org/rfc/rfc3629).
  Rechaza continuaciones aisladas, secuencias incompletas, codificaciones largas,
  surrogates y valores superiores a U+10FFFF. Los tokens devueltos son strings propietarios.
- El resto de los puntos de código no ASCII se conserva literalmente como
  contenido del token; no se consulta una base completa de categorías Unicode.

Ejemplos comprobados:

| Entrada | Tokens |
|---|---|
| `MOTOR Industrial` | `motor`, `industrial` |
| `Error E47` | `error`, `e47` |
| `HTTP_404 RTX-5090 C++` | `http_404`, `rtx-5090`, `c++` |
| `motor motor` | `motor`, `motor` |
| `ÁRBOL árbol` | `Árbol`, `árbol`: no son equivalentes. |
| `café` y `cafe` + U+0301 | Se conservan distintas representaciones; no hay NFC. |

**Límite deliberado de Sprint 2:** validar y preservar UTF-8 no es normalización
Unicode completa, segmentación multilingüe ni equivalencia entre mayúsculas con
acentos. No se aplican stemming, stopwords, sinónimos, traducción ni operadores
booleanos/frases. Estas reglas siguen CP-02 y sustituyen, para esta implementación,
el perfil Unicode más amplio propuesto anteriormente en D-01.

## Estructuras y estadísticas

`InvertedIndex` prepara por documento un mapa término→TF y longitud. Build genera
un diccionario término→`vector<Posting>`. Cada posting contiene DocumentId y TF
uint32; las listas se ordenan por DocumentId y no contienen duplicados.
Las frecuencias temporales se liberan al finalizar la construcción.

| Acceso de solo lectura | Significado |
|---|---|
| `find(normalized_term)` | Span de postings; término ausente produce span vacío. No tokeniza implícitamente. |
| `document_frequency(term)` | DF: número de documentos, no suma de TF. |
| `document_length(id)` | `optional<uint32_t>`; ausencia explícita si el ID no existe. |
| `total_token_count()` | Suma de longitudes, uint64. |
| `vocabulary_size()` | Número de términos distintos una vez construido. |

Find, DF y vocabulario requieren READY; conteo, longitudes y media describen los
documentos registrados incluso durante COLLECTING. Los vacíos cuentan en N y
la media; nunca tienen postings y no serán candidatos.

## Fórmula y reproducibilidad

Se utilizan logaritmo natural, acumulación y resultados `double`:

$$IDF(t)=\ln\left(1+\frac{N-DF(t)+0.5}{DF(t)+0.5}\right)$$

$$BM25(d,q)=\sum_{t\in unique(q)}IDF(t)
\frac{TF(t,d)(k_1+1)}{TF(t,d)+k_1\left(1-b+b\frac{|d|}{avgdl}\right)}$$

El IDF suavizado positivo y defaults coinciden con los documentados en
[Apache Lucene BM25Similarity](https://lucene.apache.org/core/10_3_1/core/org/apache/lucene/search/similarities/BM25Similarity.html).
No se afirma equivalencia numérica completa con Lucene: nuestro contrato fija
su propia tokenización, longitudes exactas y deduplicación de términos de consulta.

Los términos de consulta se ordenan y deduplican antes de acumular, conservando
un orden de suma estable. Solo se visitan sus postings. Se ordenan todos los C
candidatos y se trunca el ranking; coste esperado `O(P + C log C)`, además de
tokenización y ordenamiento de términos de consulta. No se recorre el corpus
completo para puntuar cada consulta.

`compute_idf(N,DF)` y `bm25_term_score(tf,dl,avgdl,idf,config)` son funciones
puras públicas para verificar las matemáticas. Rechazan estadísticas inválidas:
IDF requiere `0 < DF <= N`; el scorer requiere avgdl e IDF finitos positivos y
`tf <= dl`. TF=0 retorna cero con estadísticas válidas. La fórmula del scorer
se escala algebraicamente cuando k1≥1 para evitar inf/inf con k1 finito muy grande.
Los contratos vectoriales FP32 no se alteran por el uso de double en BM25.

Referencias del fixture de tres documentos mostrado al inicio:

| Consulta / documento | Valor esperado |
|---|---:|
| IDF de `e47`, N=3 y DF=1 | 0.9808292530 |
| IDF de `motor`, DF=2 | 0.4700036292 |
| `e47` / 101 | 0.8142733421 |
| `motor` / 101 | 0.5665797174 |
| `motor` / 102 | 0.4700036292 |
| `motor e47` / 101 | Suma de sus dos contribuciones. |

Las referencias se prueban con tolerancia absoluta estricta **<1e-6**, sin
convertir scores a float. Un oráculo adicional recorre arrays de tokens del
corpus original, recalcula DF/longitudes/fórmula y compara 50 consultas contra
el índice sobre 120 documentos determinísticos; no reutiliza el scorer ni
las estadísticas del módulo para construir el valor esperado.

## Corpus preliminar y adaptador para CP-01

CP-01 aún no existe, según confirmación del usuario del 25 de octubre de 2026.
Se entrega un [fixture sintético de regresión](../../tests/fixtures/bm25/README.md)
de 100 documentos y 20 consultas con un documento esperado cada una. Contiene
códigos literales y casos deliberadamente fáciles; sus resultados no certifican
relevancia real, KR1.3 ni CP-05.

Un driver independiente, construido con `BUILD_TESTING=ON`, registra Top-10,
posiciones del documento esperado y Hit Rate@10 sin implementar RRF:

```sh
./build-bm25/tests/aether_bm25_evaluate \
  tests/fixtures/bm25/documents.tsv tests/fixtures/bm25/queries.tsv \
  build-bm25/bm25-manual
```

Entradas UTF-8 sin BOM ni encabezados y sin tabs/saltos internos en los campos:

- Documentos: `DocumentId<TAB>text`.
- Consultas: `query_id<TAB>expected_document_id<TAB>query`.

Admite LF y CRLF, IDs uint32 únicos y textos documentales vacíos. Rechaza filas
mal formadas, IDs negativos/fuera de rango, consultas con ID duplicado y etiquetas
que apuntan a documentos ausentes. Si la consulta válida no tiene coincidencias,
registra un fallo de recuperación; no lo transforma en error de carga.

Produce `rankings.csv`, `queries.csv` y `summary.json`. La tasa es
`hits_at_10 / número_de_consultas`, en [0,1]. No impone la meta 18/20 ni la
certifica: CP-05 deberá usar el corpus representativo y sus etiquetas acordadas.
Un score BM25 no se usa para generar la etiqueta de relevancia.

Cuando exista CP-01, preparar este adaptador TSV y activar su lectura optativa:

```sh
cmake -S . -B build-bm25 \
  -DAETHER_BM25_CORPUS_DIR=/ruta/absoluta/al/corpus
cmake --build build-bm25 --parallel 4
ctest --test-dir build-bm25 -R '^integration.bm25_corpus_external$' -V
```

No hay descarga automática ni dependencia Python en estas pruebas. La carga de
archivos se limita al driver de evaluación; el módulo acepta `string_view`.
Con `BUILD_TESTING=OFF`, puede compilarse solo la biblioteca mediante
`cmake --build build-bm25 --target aether_lexical`, sin construir HNSW ni CLI.

La evidencia de las compilaciones, sanitizadores y límites de esta entrega se
recoge en [el informe de CP-02](../reports/CP02_BM25_VALIDATION.md).
